SpliceProb — Planner / Worker / Judge workflow (for human developers)
======================================================================

This project uses a manual multi-agent development loop with Cline. You
switch the underlying LLM model and open a session with one of three tags.
The AI reads `.clinerules` at the start of every session, detects the tag,
and locks itself into exactly one role for that whole session. It will not
switch roles mid-session — if you need a different kind of work, start a
new session with the appropriate tag.

THE THREE ROLES
----------------

[PLANNER]  — System Architect
  What it does: reads project_brief.md + architecture.md, breaks your
  request down into small, independently-completable tasks, and writes
  them into docs/ai/progress.md as a checklist.
  What it never does: touch application code, or mark any task done/failed.
  When to use it: at the start of a new feature/milestone, or whenever the
  task backlog needs restructuring.
  How to trigger it: start your message with `[PLANNER]` followed by what
  you want built.

[WORKER]  — Agile Developer
  What it does: reads docs/ai/active_context.md (to pick up where the last
  Worker session stopped) and docs/ai/progress.md (the backlog), then
  implements the FIRST unchecked task it finds — one task per session.
  What it never does: mark its own task done/failed (that's the Judge's
  call), or start a second task in the same session.
  Hard limit: if it estimates it has used ~1/3 of its context window, it
  stops immediately, saves its exact stopping point to active_context.md,
  updates progress.md with what it actually finished, and tells you to
  start a fresh session. This is intentional — it keeps each Worker
  session focused and avoids degraded output from a near-full context
  window. It is normal to need several [WORKER] sessions to close one task.
  How to trigger it: start a new session with `[WORKER]` and nothing else
  needed — it will figure out what to do from the backlog.

[JUDGE]  — Lead QA Engineer & Auditor
  What it does: reads docs/ai/audits_history.md first (so it doesn't
  repeat a mistake already made and logged before), reviews what the
  Worker(s) produced, runs tests, and then either:
    - marks the task [FAILED] in progress.md with clear next steps and
      logs the bug in audits_history.md, or
    - marks the task [DONE] in progress.md.
  It does not fix bugs itself — a failed task goes back to a [WORKER]
  session, keeping the review role separate from the implementation role.
  Once every task in the current batch is [DONE], the Judge wipes
  active_context.md clean for the next cycle, then commits everything
  with a message starting with the literal prefix `*AI COMMIT* `. That
  prefix is how you can spot AI-authored commits in `git log` at a glance.
  How to trigger it: start a session with `[JUDGE]` once you want the
  current batch of Worker output reviewed.

THE FILE LIFECYCLE (docs/ai/)
------------------------------

project_brief.md   Static reference. What the product is and why. Rarely
                    changes; read by the Planner before planning anything.

architecture.md    Living technical map: layers, data flow, known issues.
                    Updated whenever a session changes the architecture or
                    resolves/discovers a structural issue.

progress.md         The task backlog. Planner writes tasks in as `[ ]`,
                    Worker implements them, Judge flips them to `[DONE]`
                    or `[FAILED]` with notes. This is the single source of
                    truth for "what's left to do."

active_context.md   Short-lived handoff notes between Worker sessions
                    only — "here's exactly where I stopped and what's
                    next." Gets wiped blank by the Judge once a batch is
                    fully done. If you open this file and it's empty,
                    that means the last batch finished cleanly.

audits_history.md   Permanent log of bugs/mistakes the Judge has found,
                    across all sessions. Never wiped. Its whole purpose is
                    to stop the same architectural or logical mistake from
                    being reintroduced later.

A TYPICAL CYCLE
-----------------
1. You open a session, type `[PLANNER] <what you want>` → progress.md gets
   a fresh batch of tasks.
2. You open a new session, type `[WORKER]` → it implements task 1,
   possibly across a couple of sessions if it hits the 1/3 context limit.
3. Repeat step 2 for each remaining task in the batch.
4. You open a session, type `[JUDGE]` → it reviews everything, updates
   progress.md (DONE/FAILED), logs anything it finds in audits_history.md,
   resets active_context.md once the whole batch is clean, and commits
   with an `*AI COMMIT*` message.
5. Any `[FAILED]` task goes back through another `[WORKER]` session before
   the next `[JUDGE]` pass.
